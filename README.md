        # sqlite — JSON и генерируемые столбцы

        Homework-шаблон для урока **l2_json1_and_generated** (JSON и генерируемые столбцы) на платформе Vibe Learn.

        ## Что делать

        На Python (stdlib sqlite3) реализуй хранилище событий с JSON-полем data и быстрым поиском по
«горячему» полю. Функции: insert_event(conn, data_dict), find_by_user(conn, user_id) → события
пользователя, find_by_tag(conn, tag) → события с тегом в массиве. Схема: events(id, data TEXT),
плюс generated column user_id AS (json_extract(data,'$.user_id')) с индексом. find_by_user
фильтрует по индексированной колонке; find_by_tag использует json_each по '$.tags'. Тесты на
:memory:: проверяют, что (1) поиск по user_id находит нужные события, (2) `EXPLAIN QUERY PLAN`
для find_by_user показывает использование индекса (а не SCAN), (3) find_by_tag корректно
находит события по элементу массива. Бонус-тест: разница в плане до/после добавления индекса.

## Контекст (из transfer-задачи урока)

Аналитика продуктовых событий на SQLite: таблица events(id, ts, data TEXT), где data — это
JSON произвольной формы от разных версий клиента (поля приходят и уходят между релизами).
Объём ~5M строк. Два запроса в проде стали медленными: (1) `WHERE json_extract(data,'$.user_id') = ?`
(выборка событий пользователя), (2) фильтр по наличию конкретного тега в массиве
`data.$.features`. Разработчик предлагает «распарсить весь JSON в 80 отдельных колонок».

**Вопрос:** объясни:
(a) почему оба запроса сейчас медленные (что именно происходит на 5M строк);
(b) как ускорить запрос (1) — generated column vs expression index, какой вид (VIRTUAL/STORED)
    и почему;
(c) как ускорить запрос (2) по элементу массива (json_each и индекс);
(d) почему «распарсить всё в 80 колонок» — плохая идея для данных меняющейся формы, и где
    проходит граница JSON vs обычные колонки.

## Recap из урока

- JSON в SQLite хранится как **TEXT** (или бинарный **JSONB**-blob с 3.45). Отдельного JSON-типа колонки нет.
- Операторы: **`->`** возвращает JSON, **`->>`** — голый скаляр (для сравнений `WHERE ->> = '...'` нужен `->>`). Плюс `json_extract`, `json_set`, `json_each`.
- Нельзя индексировать поле внутри TEXT напрямую → фильтр по `json_extract` без подготовки делает **полный скан**.
- Чинится **generated column + индекс** или **expression index**. Generated: **VIRTUAL** (не хранится, вычисляется на чтении, но индексируется) vs **STORED** (материализован).
- JSON — для гибкого/разреженного **«хвоста»** атрибутов; **горячие** поля фильтрации/агрегации — в обычные колонки (или generated + индекс). В PostgreSQL — нативный jsonb + GIN-индекс.

        ## Как работать

        1. Платформа Vibe Learn создаёт копию этого репо в твоём GitHub-аккаунте по клику «Начать домашку» на странице урока (через GitHub `/generate`, codecrafters-pattern).
        2. Склонируй копию локально, реализуй TODO в `main.py`, прогони тесты, запушь.
        3. CI (`.github/workflows/ci.yml`) ставит зависимости и запускает `pytest` на каждый push. Платформа слушает результат через webhook от GitHub Actions и обновляет статус домашки на странице урока.

        ## Локальное окружение

        - Python 3.12+
        - SQLite встроена — **никакого сервера и docker-compose**. БД это один файл (`DATABASE_PATH`) или `:memory:` в тестах. Модуль `sqlite3` входит в stdlib, ставить драйвер не нужно — единственная зависимость это `pytest`.

        ## Запуск

        ```bash
        # Установить зависимости (только pytest)
        pip install -r requirements.txt

        # Прогнать тесты (бегут на :memory:-базе, ничего поднимать не нужно)
        pytest

        # Запустить main (печатает marker; замени stub на реализацию)
        python main.py

        # На файловой БД (нужно для backup/vacuum-уроков):
        DATABASE_PATH=./app.db python main.py
        ```
